# 하네스 구현 결정

## D-001 / 기본안 채택
- 선택: 과제 폴더 유지 + 제출 범위 목록, 제품 AI 연동은 조건부.
- 판단 주체: 사용자가 이번 대화에서 설계안의 1·2번 질문에 동의.
- 한계: 실제 제출 형식·모델·인증 경로는 공식 과제 안내로 확정해야 한다.

## D-002 / F-001~F-005
- 선택: Python 3.10+ 표준 라이브러리, 외부 패키지·전역 설치 없음.
- 판단 주체: Codex 구현 판단. 현재 Python 3.14.3 환경을 확인하고 선택.
- 이유: 설치 비용과 의존성 실패를 줄이고 Mac·Linux에서 검토하기 쉬운 구성.
- 대안: Node·셸 중심 구현. 현재 필요한 작업에 Python이 이미 있어 추가하지 않음.
- 한계: Python 3.10 문법 검사는 했지만 실제 실행 검증은 3.14.3/macOS만 수행.

## D-003 / F-002~F-003
- 선택: unittest는 별도 프로세스의 구조화된 개수, 명령은 명시 조건, 수동은 확인 대기 후 보고.
- 이유: 종료 코드 0이나 로그의 PASS 문구만으로 실제 검사를 통과시키지 않기 위함.
- 판단 주체: Codex 구현 판단.
- 실제 경로: tools/_unittest_runner.py, _core.py: run_check/confirm/current_status.
- 한계: 기대값의 적절성, 수동 보고의 진실성, scope 밖 변경은 자동 보증하지 않음.

## D-004 / F-003
- 선택: 실행별 JSON은 보존하고 현재 상태는 파일 지문으로 다시 계산.
- 이유: 커밋되지 않은 코드도 식별하면서 로그 추가가 자기 검증을 무효화하지 않게 함.
- 판단 주체: Codex 구현 판단.
- 실제 경로: tools/_core.py: snapshot/record/current_status.
- 한계: 새 의존성이 생기면 계약과 scope를 갱신해야 함. 내용 식별은 악의적 변조 방지 서명이 아님.

## D-005 / F-001·F-006
- 선택: 기본 설치는 미리보기, --apply 적용, 기존 문서 보존, 충돌 시 쓰기 전 중단.
- 이유: 원래 프로젝트와 Git index를 보호하고 규칙 적용을 검토 가능하게 함.
- 판단 주체: Codex 구현 판단.
- 한계: 기존 AGENTS가 있으면 비교·반영 필요. 자동 스킬 인식은 확인하지 않음.

## 설명: 입력부터 결과까지
사용자가 checks.json에 실제 계약의 검사 ID를 등록한다.
check.py가 CLI 입력을 받고 _core.py가 경로·설정·지문을 확인한다.
자동 검사는 별도 프로세스에서 실행하고 결과·개수·원본 상태를 대조한다.
수동 검사는 대기 기록을 만든 뒤 관찰 보고와 같은 코드 상태를 연결한다.
결과는 artifacts/evidence에 남고 status가 현재 파일과 비교하여 유효성을 보여준다.
release는 필수 task 검사·최종 수동 확인·원본·제출 목록을 결합하며 업로드는 하지 않는다.
