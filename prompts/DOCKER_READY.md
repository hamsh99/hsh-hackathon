# Docker 실행 준비 요청

## 사용할 때

컨테이너 실행이나 배포를 고려한 구현이 요구될 때 적용한다. 요구가 없으면 자동으로 Docker를 도입하지 않는다.
처음 설계할 때 실행 구성·저장 위치를 정하고, 첫 실행 가능한 흐름에서 빌드·기동을 확인한다. 마지막에만 처음 실행해 보지 않는다.
아래는 현재 허용 범위에 맞춰 적용하는 요청문이며 모든 프로젝트의 기술 스택을 동일하게 바꾸는 지시가 아니다.

## 용어

| 용어 | 뜻 |
|---|---|
| Dockerfile | 프로그램과 필요한 실행 환경을 이미지로 만드는 조리법 |
| 이미지 | 실행에 필요한 내용을 준비한 패키지 |
| 컨테이너 | 이미지로 실제 실행 중인 프로그램 |
| Docker Compose | 여러 프로그램의 실행·연결·저장 설정을 한곳에서 관리하는 도구 |
| compose.yaml | 어떤 컨테이너를 어떤 설정으로 함께 실행할지 적은 파일 |
| 볼륨 | 컨테이너를 다시 만들어도 데이터를 보관할 수 있도록 연결하는 별도 저장 공간 |
| 환경변수 | 실행할 때 밖에서 전달하는 설정값 |
| 헬스체크 | 프로그램이 요청을 처리할 준비가 되었는지 확인하는 검사 |

Compose는 외부 공개를 뜻하지 않는다. 별도 DB와 웹 프로그램을 함께 실행할 때 유용하며, 프로그램 하나의 단순한 실행에도 선택적으로 쓸 수 있다.
Dockerfile이 있다고 데이터가 보존되거나 서비스가 정상 동작하는 것은 아니다. 각각 실제로 검사해야 한다.

## 요청문

```text
공통 규칙과 PROBLEM의 실행·데이터 보존 요구사항, PLAN의 허용 범위와 기존 코드를 읽어줘.
다른 환경에서도 재현할 수 있는 가장 단순한 실행 구성을 만들어줘.

1. 기존 기술 스택에 맞는 구성을 선택하고 프로그램·DB·저장 위치를 쉽게 설명해줘.
프로그램과 DB 등을 함께 실행할 설정이 필요하면 Docker Compose 구성 파일을 작성해줘.
필요한 이유를 설명하고, 단순한 구성에서는 불필요하게 추가하지 마.
2. 설정값과 비밀값을 환경변수로 주입하고 실제 비밀값이 없는 .env.example을 작성해줘.
비밀값을 코드·이미지·문서·로그에 넣지 말고 실제 설정 파일이 이미지에 포함되지 않도록 해줘.
필수 설정이 없을 때의 안내와 초기 계정 준비 방법도 정해줘.
3. DB 저장·데이터 보존이 요구되는 경우 필요한 데이터·생성 결과를 DB에 저장하고, 컨테이너를 재시작·교체해도 남도록 저장 공간을 연결해줘.
빈 DB에서 스키마와 초기 데이터가 준비되고, 다시 실행해도 데이터가 중복되거나 덮어써지지 않게 해줘.
DB가 필요 없는 과제에 DB를 새로 도입하지 말고, 해당 없는 검사는 이유와 함께 구분해줘.
4. Dockerfile과 필요한 의존성·실행 설정을 작성하고, 웹 서비스에 요구되는 헬스체크 엔드포인트를 제공하고, 다른 실행 형식이면 과제에 맞는 상태 확인 방법을 사용해줘.
주소·포트·설정 파일·호스트에만 있는 숨은 의존성 때문에 다른 환경에서 실행되지 않는 문제가 없는지 확인해줘.
5. 기존 데이터를 훼손하지 않는 별도 검사 환경에서 실제 빌드·기동과 해당하는 헬스체크를 확인해줘.
DB·데이터 보존이 요구되면 빈 DB 준비·저장, 컨테이너 재시작과 같은 저장 공간을 연결한 재생성 후 보존, 재초기화의 중복 방지도 확인해줘.
실제 명령·입력·결과와 실행하지 못한 항목을 현재 라운드에 남겨줘.
6. 실행 명령, 필요한 환경변수, 역할별 접속 방법을 과제에서 지정한 실행 안내 문서에 기록해줘.
지정이 없으면 기존 프로젝트의 실행 안내 문서를 활용하고, 없으면 간단한 문서를 준비해줘.
실제 문서 위치는 PLAN에 연결하고 과제의 원본 README는 보존해줘.

실제 외부 배포는 수행하지 마.
제공된 개발 환경 안에서 실행하고, 컨테이너 빌드·기동·데이터 보존까지 검증해줘.
문서 작성이나 Dockerfile 생성만으로 실행 검증을 완료 처리하지 마.
```

## 완료를 판단할 근거

- 현재 코드와 문서의 명령으로 빌드·기동했는가?
- 필수 설정 누락과 해당하는 헬스체크를 확인했는가? DB가 요구되면 빈 DB 준비와 초기화 재실행도 확인했는가?
- 데이터 보존이 요구되면 실제로 저장한 입력·결과가 재시작·컨테이너 재생성 후에도 같은 저장 공간에서 조회되는가?
- 검사에 사용한 DB·볼륨을 기존 작업 데이터와 구분했고, 실행 불가·미실행을 따로 남겼는가?

빌드 환경이나 Docker가 없으면 원인과 미확인 검사를 기록한다. 정적 파일 점검을 실행 성공으로 대신하지 않는다.
기존 역할이 있는 문서·설정은 재사용하며, 이 요청문을 읽었다고 별도 서버·DB·컨테이너 수를 고정하지 않는다.
